# Paper-mode webhook intelligence release review (final)

The final state adds authenticated webhook management, secret-authenticated TradingView ingestion, paper execution, monitoring, and a protected dashboard route. The recent fixes close the scoped gaps in bounded derived deduplication, configured-risk enforcement, ambiguous exits, leveraged P&L, webhook-only metrics, history refresh, canonical URLs, and frontend API-base selection. Two failure-recovery defects and one unauthenticated control surface still block paper-mode release. **Watch for:** **confirmed** public Binance controls can alter another user’s state; **confirmed** paper persistence failures receive HTTP 202; **confirmed** failed claimed events cannot be retried with the same identity.

**Verdict**: NEEDS_CHANGES

## High-level view

The v1 management APIs require Firebase authentication, webhook ingestion requires an endpoint secret, and both v1 and legacy live execution are gated. The newly added Binance connect and synchronization routes remain outside that authorization boundary and accept caller-supplied user IDs.

Paper entries verify the trade write and paper exits report journal-write failures. The common ingest response still returns HTTP 202 for those failures, acknowledging delivery before the requested paper operation is durably complete.

Events are claimed before execution. A retry with the same explicit identity becomes a permanent duplicate rather than resuming the failed operation; derived identities remain blocked for their five-minute bucket.

1. **Unauthenticated Binance controls — confirmed** — Public Binance routes trust caller-supplied user IDs and can mutate or control another user’s state. Require Firebase authentication plus UID matching on every route, or remove them from the paper deployment.
2. **Persistence failures acknowledged with 202 — confirmed** — Failed paper trade or journal writes still receive a successful HTTP acknowledgement. Return a retryable non-2xx response such as 503.
3. **Failed claims remain deduplicated — confirmed** — A failed operation cannot resume under the same explicit alert identity, and derived alerts are blocked for five minutes. Add retry/resume and exit-reconciliation behavior for incomplete claims.

<details><summary>Details</summary>

## Binance synchronization remains outside the user authorization boundary

**Confirmed:** `backend/app.py` applies `require_firebase_user` to portfolio, trade, mode, webhook-key, and legacy exchange-connect handlers, but not to `/api/binance/connect`, `/api/binance/start-sync`, `/api/binance/stop-sync`, `/api/binance/sync-status/<user_id>`, `/api/binance/sync-now`, or `/api/binance/positions/<user_id>`. These handlers trust a body or path `userId`; connect and stop directly update that user’s Firestore document, while start/stop control synchronization by that identifier. An unauthenticated caller can write connection metadata, stop another user’s synchronization, inspect status, or start work under an arbitrary application user ID.

This blocks paper-mode release because it permits cross-user mutation on the same public backend. Apply Firebase bearer authentication to every Binance route and require the authenticated UID to match the body/path UID, or remove these routes from the paper deployment.

## Failed paper writes still receive a successful delivery acknowledgement

**Confirmed:** `_paper_entry` returns `failed` when the `webhook_trades` write cannot be persisted, and `_paper_exit` returns `failed` when the closed-trade journal write fails. The ingest handler maps either result to `status = "failed"` but returns the common response with HTTP 202. Webhook senders use the HTTP status to decide whether delivery succeeded, so a storage outage is acknowledged and the alert can be dropped without retry.

Return a retryable non-2xx response such as 503 whenever paper execution reports a persistence failure.

## Claimed failures cannot be resumed under the same alert identity

**Confirmed:** `_claim_event` creates the durable event before risk checking and paper execution. A later persistence failure leaves that ID claimed, and the duplicate branch does not check whether the prior operation failed or its trade/journal is missing. Explicit `idempotencyKey`, `alertId`, or `uuid` values therefore remain duplicates indefinitely; derived identities remain blocked throughout the five-minute bucket.

A 503 response alone is insufficient because a conforming retry still cannot complete. Failed claims need a retry/resume state that safely repairs a missing trade or journal; exit reconciliation must account for the trade possibly closing before its journal write failed.

</details>

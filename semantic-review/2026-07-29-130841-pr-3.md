# TradingView webhook intelligence backend (final review)

The change adds a self-contained Flask blueprint for authenticated webhook administration, public TradingView ingestion, deterministic duplicate detection, paper execution, and bounded operational reporting. It keeps live trading fail-closed and registers the blueprint with the existing Firestore client while preserving the legacy routes. The trust boundary is largely in place, but paper accounting and position lifecycle behavior are not yet safe to ship. **Watch for:** **confirmed** leveraged paper trades overstate P&L; **confirmed** concurrent exits can both report filling the same position; **confirmed** bounded reads do not select the most recent records.

**Verdict**: NEEDS_CHANGES

## High-level view

Paper entries and exits use the expected per-user collections, but three **confirmed** lifecycle defects affect downstream behavior: exit P&L applies leverage to an already quantity-based price movement, selection and closure of an open trade is not atomic, and open trades can be classified as closed by overview metrics. These defects can corrupt Dashboard, History, Analytics, and Calendar results even though the single-entry/single-exit smoke path succeeds.

The control APIs filter a bounded Firestore sample in memory to avoid composite indexes. The **confirmed** unordered fetch means that sample is not necessarily recent, so filtering, pagination, event detail associations, and overview aggregates become incomplete or stale beyond the fetch cap.

Management APIs derive the tenant only from a verified Firebase token, endpoint secrets are stored as hashes and compared in constant time, raw credentials are redacted, and live execution never reaches the legacy global exchange. A **likely** deployment gap remains for endpoint IP allowlists because ingestion evaluates `request.remote_addr`; behind a reverse proxy this is normally the proxy address rather than the TradingView source address.

In live mode, a **confirmed** audit inconsistency marks `order_created` complete before recording that execution was blocked, even though no adapter or order exists.

<details>
<summary>Issues (7)</summary>

1. **Leveraged paper P&L** — **confirmed:** paper exits multiply quantity-based P&L by leverage, overstating journal results. Remove leverage from absolute P&L and retain it only in margin/ROI calculations.
2. **Non-atomic position closure** — **confirmed:** concurrent exit events can both fill the same open trade. Use a Firestore transaction or precondition and make fallback selection-and-close one locked operation.
3. **Open trades counted as closed** — **confirmed:** open paper positions carry `pnl: 0` and are included in closed-trade metrics. Require closed status or a closed timestamp for trade metrics.
4. **Arbitrary bounded samples** — **confirmed:** Firestore reads apply a limit without timestamp ordering, so controls and metrics can omit recent or matching records. Fetch newest-first before client-side filtering.
5. **Proxy-unaware IP allowlist** — **likely:** hosted deployments will compare allowlists to the reverse proxy address. Configure trusted proxy-hop handling and verify source-IP behavior in the real hosting topology.
6. **False live order stage** — **confirmed:** blocked live events report `order_created` as completed. Move that stage into an executing branch or mark it skipped when no adapter exists.
7. **Missing failure-mode regression tests** — **confirmed:** validation does not cover the accounting, concurrency, bounded-read, proxy, or live-timeline cases above. Add focused tests, including proof that only one concurrent exit can close a position.

<details><summary>Details</summary>

## Leveraged paper exits overstate journal P&L

At `backend/webhook_intelligence.py:613`, paper exit P&L is calculated as `(exit_price - entry) * quantity * leverage * direction`. Quantity already represents the instrument position size, while leverage has reduced the recorded margin at entry. **Confirmed:** multiplying the price movement by leverage again makes absolute P&L too large by the leverage factor; one unit moving from 100 to 110 at 10x records 100 rather than 10 before fees. Remove leverage from absolute P&L and retain it only through the margin-based ROI calculation.

A separate **confirmed** classification error exists at `backend/webhook_intelligence.py:695`: `_trade_metrics` treats any record with a non-null `pnl` as closed, while new paper entries store `pnl: 0`. When no journal exists and overview falls back to `webhook_trades`, open positions inflate `closedTrades` and dilute win/loss rates. Closed metrics should require a closed status or timestamp.

## Paper position closure is not atomic

`_paper_exit` reads up to 200 open positions, chooses the newest match, then updates the position and writes its journal in separate operations (`backend/webhook_intelligence.py:594-655`). **Confirmed:** two distinct exit events handled concurrently can both observe the same position as open, both return `filled`, and both compute outcomes for it; the later journal write overwrites the earlier one because both use the entry trade ID. Firestore closure needs a transaction or update precondition that verifies the selected trade is still open, and the in-memory fallback needs one lock around selection and closure.

## Bounded control reads are not bounded to recent data

`_fetch_user_docs` applies `.limit(...)` without an `order_by` at `backend/webhook_intelligence.py:278`, then sorts and filters only after fetching. **Confirmed:** Firestore can return a document-ID-ordered subset; with hash event IDs, recent events and matching filter results can be omitted while older unrelated records occupy the 500-document sample. Fetch newest-first by each collection's relevant timestamp before client-side filtering, including events, executions, errors, trades, and overview inputs.

## Endpoint allowlists depend on proxy-aware source IP handling

Ingress checks the allowlist against `request.remote_addr` at `backend/webhook_intelligence.py:811`. **Likely:** behind a reverse proxy this identifies the final proxy hop, causing configured TradingView ranges to be rejected and stored source IPs to be misleading. Configure trusted proxy-hop handling at the deployment boundary and test the actual hosting topology; forwarded headers must not be trusted directly from arbitrary clients.

The surrounding security design keeps Firebase-authenticated tenant identity separate from public endpoint authentication, redacts credential-shaped raw fields, and leaves live execution isolated from the global exchange.

## Live-mode timeline claims an order that never existed

The common path records `order_created` as completed at `backend/webhook_intelligence.py:873` before checking whether the endpoint is live. **Confirmed:** live requests then append `execution_blocked`, producing an execution log that claims order creation despite the tenant-safe adapter being absent. Move order creation into the paper branch or mark it skipped for live mode.

## Validation misses the failure modes above

The reported compile check and Flask test-client smoke test cover endpoint creation, authenticated rejection, normal paper entry/exit, duplicate handling, and control reads. **Confirmed:** they do not exercise leveraged P&L arithmetic, simultaneous exits, open-only overview metrics, more than 500 persisted records, proxy-derived source addresses, or live-mode stage semantics. Add focused tests after correcting the behavior; the concurrency test should prove that exactly one exit can transition a position from open to closed.
